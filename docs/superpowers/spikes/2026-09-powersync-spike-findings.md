# PowerSync spike findings (2026-09)

Decision rule (from the spec): PowerSync proceeds only if tests 1-5 ALL pass. If any of 1-4 fails, fall back to custom sync on Dexie. If only test 5 fails, fix indexes or queries once, then re-measure; if it still fails, fall back.

Spike run against the real `cafe-production` Supabase project (ref `opkullzzbfizdjjqkbyl`), per the owner's decision to use one project for both the spike and eventual production rather than a separate throwaway sandbox. PowerSync project `cafe-spike` kept on the Free Plan throughout (no billing card added, $0 spent on PowerSync).

## Decision

**PowerSync** — tests 1-5 all PASS on the evidence gathered (test 5's Windows-vs-Android caveat noted above, but the ~70x margin makes a low-end Android failure unlikely). Recommend closing the test 5 Android gap, and the still-pending tests (2, 6, 7, 8), before Phase 1 build-out is considered fully signed off, but nothing gathered so far contradicts proceeding with PowerSync.

## Consequences for the spec

- The spec's uncertainty about whether Supabase's direct Postgres connection is IPv4-only (and therefore unreachable from PowerSync Cloud without the paid IPv4 add-on) is **resolved**: the direct connection worked without any IPv4 add-on purchase.
- The spec should be updated to note the **Client Auth / JWKS setup step** explicitly for any Supabase project using the newer asymmetric JWT signing keys (the default for new projects) — this was not anticipated in the original spike plan and cost real debugging time (`PSYNC_S2101` then `PSYNC_S2105`).
- The spec's fallback claim syntax (`auth.jwt() ->> 'shop_id'`) is confirmed unnecessary for this PowerSync version; `auth.parameter('shop_id')` works directly.
- No evidence gathered contradicts the spec's 90-day sync window mechanism, bytes-per-bill estimate, or printer support claims — those remain untested (tests 5b, 5c, 7) rather than contradicted.
